1. Executive Architectural Overview

TIVIDY is a generic Workflow Management System (WfMS) adhering strictly to the standard Workflow Management Coalition (WfMC) architectural reference model. Its core purpose is to define, validate, instantiate, execute, inspect, and recover automated business processes composed of human tasks, automated external services, dynamic decision branches, and multi-tier organizational approval hierarchies.

🌟 The Foundational Axiom of TIVIDY
Processes are DATA, not CODE. There are no hardcoded classes called UniversityAdmissionTask, HospitalSurgeryTask, ShipmentRerouteTask, or InsuranceClaimTask. All business logic, control flows, task hierarchies, and routing rules are declared externally in declarative text files. The exact same compiled C++ executable interprets these files using pure polymorphic GoF patterns without requiring recompilation or relinking.

The system lifecycle follows five distinct operational phases:

1. Build Time Builder / Director

FileWorkflowDefinitionBuilder parses definitions/*.definition. WorkflowDirector coordinates the step-by-step assembly of stages, tasks, dependency rules, routing strategies, decorators, and external service linkages into an immutable WorkflowDefinition blueprint.

2. Scenario Binding ParticipantDirectory

context/*.context files define human participants, their organizational roles, starter permissions, and UI input/completion fields. Each scenario is registered into an isolated roster in ParticipantDirectory, cleanly separating workflow structural logic from organizational rosters.

3. Instantiation & Isolation Prototype

WorkflowEngine::createInstance() deep-clones the definition's composite tree via WorkItem::clone() into an independent WorkflowInstance with isolated InstanceData, a fresh DependencyMediator, and newly initialized state machines.

4. Execution & Governance State / Mediator / Command

Human participants interact through TividyWorkflowFacade executing discrete WorkItemAction commands (ClaimAction, StartAction, CompleteAction, RejectAction, DelegateAction, CancelAction). DependencyMediator evaluates downstream rules to advance or prune branches.

5. Telemetry, SLAs & Undo Observer / Memento

Every lifecycle transition broadcasts through the EventDispatcher Meyers' Singleton to AuditLogger, NotificationService, and MonitoringService. WorkflowSnapshot captures pre-action snapshots enabling full transactional rollback via undoLast().

4. Generic TUI Architecture Deep Dive

In earlier prototypes, user interfaces in academic projects often rely on hardcoded switch statements tailored to specific scenarios. In TIVIDY, the interactive Terminal User Interface (src/main.cpp) was completely re-engineered into a 100% generic, metadata-driven presentation layer that operates exclusively through TividyWorkflowFacade:

Dynamic Discovery & Binding

At startup, Tui::initialise() scans the physical folders definitions/ and context/ via POSIX directory traversal. It parses every .definition via facade.registerDefinitionFromFile(), loads every .context, matches them by workflow ID, and links descriptions via facade.definitionDescription(). The C++ code knows zero workflow names!

Isolated Participant Rosters

Each context automatically creates its own participant roster in ParticipantDirectory using the file stem (e.g. education, logistics, healthcare). Participant IDs and role names are completely partitioned, allowing identical user IDs or roles across completely different industries without namespace collisions.

Dynamic Form & Task Prompts

Instance initiation prompts are dynamically generated from FIELD entries in the context file. When completing tasks, TASK_FIELD entries dynamically generate prompt fields. Decision choices are rendered from OUTCOMES lines. If no outcomes are specified, it falls back to a free-form outcome prompt.

The "Refusal Inspection" Principle

Unlike fragile UIs that hide disabled buttons, TIVIDY deliberately keeps all six actions selectable (Claim, Start, Complete, Reject, Delegate, Cancel). When an invalid action is chosen, the engine's WorkItemState or RoutingStrategy rejects it, and the TUI prints the exact invariant explanation (e.g., "Refused by the engine: task is in AvailableState, cannot complete"). This directly proves to markers that business invariants are strictly enforced by the engine core, not masked by the UI!

6. What Makes Code "Generic" vs. "Non-Generic"?

In the COS 214 project defense, examiners will repeatedly test whether your engine is genuinely generic or merely a facade over hardcoded domain logic. Here is the rigorous architectural evidence:

❌ Hardcoded / Non-Generic (Zero Marks)

  • Creating classes named after business domains: BursaryApplicationTask, ShipmentInspectionTask, SurgerySubProcess.
  • Hardcoding business branching in C++: if (isBursary) doThis(); else doThat();
  • Hardcoding role names or user IDs directly into task code.
  • Requiring code modifications and C++ recompilation to introduce a new industry.
  • Building different executables or different engines for different business workflows.

✅ Generic / Extensible (TIVIDY Architecture)

  • Every task is a polymorphic Task; every stage is a SubProcess.
  • All control flow is governed by generic DependencyRule tuples evaluated by DependencyMediator.
  • Routing strategies operate purely on generic string roles and dynamic InstanceData key-value mappings.
  • 5 Diverse Industries run on the exact same compiled binary (./tividy) without changing one line of C++ code!
  • New workflows are added by simply dropping a .definition and a .context file into the directories.
💡 The Boundary: What IS Allowed to Vary?
Only two things change when introducing a brand-new industry:
  1. The Declarative Files (`definitions/*.definition` & `context/*.context`): Defines the task tree topology, role allocations, UI prompts, and dependency rules.
  2. External Service Adapters (`ExternalService` subclasses): When a workflow connects to an external proprietary system (e.g. Home Affairs ID database, bank payment API, or courier tracking system), an adapter translates between that external API and TIVIDY's standard ServiceRequest / ServiceResult interface.

7. The 14 GoF Design Patterns in TIVIDY

The project specification requires a minimum of 10 patterns (at least 2 creational, 2 structural, and 2 behavioural). TIVIDY implements 14 GoF patterns with clear architectural justification:

1. Builder (Creational) FileWorkflowDefinitionBuilder / Director

GoF Roles: Director = WorkflowDirector | Builder = WorkflowDefinitionBuilder | ConcreteBuilder = FileWorkflowDefinitionBuilder | Product = WorkflowDefinition.

Design Problem: Constructing a multi-level workflow definition from a declarative blueprint requires strict ordering: creating stages, resolving parent references, attaching routing strategies, registering dependency rules with the mediator, and wrapping nodes with decorators. Builder encapsulates this parsing and construction sequence, isolating it from the engine core.

2. Prototype (Creational) WorkItem::clone()

GoF Roles: Prototype = WorkItem (declares virtual WorkItem* clone() const = 0;) | ConcretePrototypes = Task, SubProcess, PriorityDecorator, AuditDecorator.

Design Problem: A WorkflowDefinition acts as a shared, immutable blueprint. Running instances must never mutate the definition's state or hierarchy. WorkflowDefinition::instantiateTree() clones the entire composite tree, producing completely isolated instances with independent state machines and instance data.

3. Singleton (Creational) EventDispatcher

GoF Roles: Singleton = EventDispatcher (accessed via EventDispatcher::getInstance()).

Design Problem: In a deeply nested composite tree, work items and state transitions need to publish lifecycle events system-wide. Passing an event-bus pointer through dozens of constructors would severely pollute the design. Implemented as a C++11 Meyers' Singleton (function-local static variable), guaranteeing thread-safety, lazy initialization, and zero memory leaks.

4. Composite (Structural) WorkItem / SubProcess / Task

GoF Roles: Component = WorkItem | Leaf = Task | Composite = SubProcess.

Design Problem: Work items exist at different levels of abstraction: atomic tasks and multi-task stages. Composite allows callers (the engine, mediators, iterators) to treat individual tasks and composite branches identically for operations like makeAvailable(), cancel(), and depth-first traversal.

5. Decorator (Structural) PriorityDecorator / AuditDecorator

GoF Roles: Component = WorkItem | Decorator Base = WorkItemDecorator | ConcreteDecorators = PriorityDecorator, AuditDecorator.

Design Problem: Tasks require orthogonal runtime capabilities (such as urgency escalation weighting or dedicated audit trail logging) without creating a combinatorial explosion of subclasses (avoiding UrgentAuditedTask). Because WorkItemDecorator inherits from WorkItem, decorated tasks fit seamlessly inside SubProcess trees.

6. Adapter (Structural) 4 Service Adapters

GoF Roles: Target = ExternalService | Adapters = GovernmentIDAdapter, BankGatewayAdapter, TrackingServiceAdapter, CarrierAdapter | Adaptees = NationalIdRegistry, BankPaymentGateway, CourierTrackingApi, CarrierBookingSystem | Registry = ServiceRegistry.

Design Problem: External legacy APIs use incompatible interfaces, return codes, and data formats. Adapters wrap these systems, translating TIVIDY's standard ServiceRequest into adaptee calls and converting responses into a uniform ServiceResult.

7. Facade (Structural) TividyWorkflowFacade

GoF Roles: Facade = TividyWorkflowFacade | Subsystem = WorkflowEngine, WorkflowDirector, ParticipantDirectory, ServiceRegistry, EventDispatcher.

Design Problem: Starting and controlling a workflow instance requires coordinating directors, builders, engine registries, action command wrapping, participant directory lookups, and observer dispatchers. The Facade provides a clean, unified API for terminal or graphical user interfaces.

8. State (Behavioural) WorkItemState (8 States)

GoF Roles: Context = WorkItem | State Interface = WorkItemState | ConcreteStates = Created, Available, Assigned, InProgress, Completed, Rejected, Escalated, Cancelled.

Design Problem: Eliminates large switch statements and boolean status flags. Each state encapsulates the legal transitions from that point in the lifecycle and refuses illegal operations with clear domain messages.

9. Strategy (Behavioural) RoleBased / DataRule / Approval

GoF Roles: Strategy Interface = RoutingStrategy | ConcreteStrategies = RoleBasedRouting, DataRuleRouting, ApprovalRouting.

Design Problem: Tasks allocate work according to different business policies (role qualifications, form data values, or multi-tiered approval chains). Strategy encapsulates these algorithms so they can be swapped dynamically.

10. Observer (Behavioural) EventDispatcher / 3 Listeners

GoF Roles: Subject = EventDispatcher | Observer = WorkflowEventListener | ConcreteObservers = AuditLogger, NotificationService, MonitoringService.

Design Problem: Multiple independent subsystems (audit loggers, monitoring metrics, notifications) need to react to workflow lifecycle events without the core engine being tightly coupled to them.

11. Mediator (Behavioural) DependencyMediator

GoF Roles: Mediator = WorkflowMediator | ConcreteMediator = DependencyMediator | Colleagues = WorkItem, Task, SubProcess.

Design Problem: Work items must trigger subsequent tasks, evaluate branches, synchronize parallel joins, and propagate rejections without tasks having direct references to each other. DependencyMediator centralizes all inter-item sequencing as data rules.

12. Chain of Responsibility (Behavioural) ApprovalHandler Chain

GoF Roles: Handler = ApprovalHandler | ConcreteHandler = ConcreteApprovalHandler | Rules = ThresholdRule, AlwaysAcceptRule | Request = ApprovalRequest.

Design Problem: Approval requests may require sign-off from different organizational tiers based on financial amounts or authority limits. Handlers pass requests along the chain until a qualified participant approves.

13. Command (Behavioural) WorkItemAction Hierarchy

GoF Roles: Command = WorkItemAction | ConcreteCommands = ClaimAction, StartAction, CompleteAction, RejectAction, DelegateAction, CancelAction | Invoker = WorkflowEngine.

Design Problem: Encapsulates user requests as standalone objects, enabling validation, history logging, checkpoint snapshotting, and transaction rollback.

14. Memento & Iterator (Behavioural) WorkflowSnapshot / Iterators

GoF Roles (Memento): Memento = WorkflowSnapshot | Originator = WorkflowInstance | Caretakers = WorkItemAction, HistoryLog.

GoF Roles (Iterator): Iterator = Iterator<T> | ConcreteIterators = DepthFirstWorkItemIterator, ApprovalChainIterator.

Design Problem: Memento captures internal instance state before each command without violating encapsulation, allowing complete rollback on undo(). Iterator traverses composite trees and approval chains without exposing internal collections.

8. WorkItem State Machine & Invariants

Every WorkItem delegates its lifecycle to an instance of WorkItemState. Transitions are strictly enforced:

Current State Allowed Transitions Triggered By Terminal? Invariant Guarantees
Created → Available, → Cancelled makeAvailable() / cancel() No Initial un-ready state. Waiting for incoming dependency rules to resolve.
Available → Assigned, → Escalated, → Cancelled assign(p) / escalate() / cancel() No Ready for work. Displayed to qualified participants for claiming.
Assigned → InProgress, → Assigned (reassign), → Escalated, → Cancelled start() / delegate() / escalate() / cancel() No Bound to a specific participant. Can be started or delegated to a peer.
InProgress → Completed, → Rejected, → Escalated, → Cancelled complete(outcome) / reject(reason) / escalate() / cancel() No Active execution. Service calls invoke here. Service failure triggers escalation.
Escalated → Assigned, → Cancelled assign(p) (reclaimed by higher authority) / cancel() No Alert condition. Operations blocked until reclaimed by a supervisor or cancelled.
Completed None (all mutations refused) Terminal state Yes Successful finish. Triggers DependencyMediator to activate downstream items.
Rejected None (all mutations refused) Terminal state Yes Business refusal. Propagates upstream to cancel downstream dead branches.
Cancelled None (all mutations refused) Terminal state Yes Pruned branch or manually aborted item. Irreversible terminal state.

★ 10. Masterclass: Logistics Failure & Exception Handling (Live Demo Segment)

This section is designed specifically for your live presentation segment. In real-world enterprise workflows, failure handling separates toy demonstrations from production-grade engineering. In TIVIDY, when an external API fails, a parcel is destroyed, or a carrier has no capacity, the engine does not crash or corrupt its state—it executes polymorphic recovery, cascading branch aborts, and automatic task escalations.

🎯 Your Presentation Goal in 3 Sentences
You are presenting the Logistics Exception & Failure Pathways. You will show examiners how TIVIDY gracefully handles: (1) External Service API outages (Tracking lookup failure → automatic task escalation), (2) Fatal physical rejections (Warehouse damage → cascading mediator branch abort), and (3) Undo recovery (Rolling back an escalated task to InProgress using Memento).

Part A: Failure Mode 1 — External Tracking API Failure & Automatic Escalation

14. Tough Marker Q&A (Top 15 Questions & Defense Answers)

Q1: Can undoLast() undo an external bank payment EFT or courier dispatch?

"No. External distributed network calls produce irreversible external side effects. TIVIDY's Memento pattern (WorkflowSnapshot) restores the exact internal state of the instance: item states, assignees, and mediator progress. This allows the participant to correct the input data and retry without corrupting workflow integrity, while the immutable AuditLogger retains an unalterable history of the external call."

Q2: What is the fundamental difference between your Observer and Mediator patterns?

"Observer (EventDispatcher) is a one-way, decoupled broadcast mechanism for passive telemetry (AuditLogger, NotificationService, MonitoringService). Observers never alter or dictate workflow control flow. Mediator (DependencyMediator) is a bidirectional coordinator: it inspects rule conditions, synchronizes parallel joins, decides which branches activate, and actively commands tasks to become available or cancel."

Q3: Why do WorkItemDecorator and SubProcess both inherit from WorkItem?

"This demonstrates the classic synergy between Composite and Decorator. Because WorkItemDecorator IS-A WorkItem, a decorator can wrap any leaf Task or composite SubProcess transparently. SubProcess::replaceChild() swaps an unadorned child with its decorated wrapper without disturbing tree traversal, parent-child ownership, or depth-first iterators."

Q4: How does your Singleton guarantee thread-safety and avoid memory leaks?

"EventDispatcher is implemented as a C++11 Meyers' Singleton (using a function-local static variable). Under C++11 standard §6.7 [stmt.dcl], initialization of a local static variable is guaranteed thread-safe by the compiler and runtime. Because it is statically allocated rather than heap-allocated with raw `new`, its destructor is automatically called at program termination, eliminating memory leaks."

Q5: How does DependencyMediator handle complex parallel joins?

"When a task or sub-process has multiple incoming dependency rules, the mediator tracks their status. It requires every incoming rule to reach a terminal decision (Satisfied or Dead). If at least one rule is Satisfied, the target item is made Available via makeAvailable(). If all incoming branches died (e.g. through rejections), the mediator automatically cancels the downstream item to prevent orphaned tasks."

Q6: What happens if an external service fails or times out?

"Task::executeService() catches the failure from the adapter. Rather than throwing an unhandled exception or permanently killing the business process with a rejection, the engine calls target->escalate(). InProgressState transitions into EscalatedState, increments the escalation counter, and fires an ESCALATED event. The task remains safely inspectable, allowing an authorized supervisor to intervene or re-attempt."

Q7: How does Chain of Responsibility integrate with the Strategy pattern for task routing?

"ApprovalRouting implements the RoutingStrategy interface. Internally, instead of a simple role lookup, it holds a pointer to the head of an ApprovalHandler chain. When canClaim() or route() is invoked, ApprovalRouting creates an ApprovalRequest and passes it down the chain. Each ConcreteApprovalHandler evaluates financial or authority thresholds (e.g. ThresholdRule) to determine whether it can handle the request or pass it to the next tier."

Q8: Why did you separate .definition from .context files?

"Separation of Concerns. The .definition file represents the pure, reusable business process topology (WfMC process model). The .context file represents the organizational binding: human participant rosters, user credentials, and interactive UI prompt configurations. This allows the exact same process definition to be deployed across different branches or departments with completely different human rosters without touching the workflow definition."

Q9: How do you prevent memory leaks when cloning composite trees?

"Every WorkItem subclass implements an explicit virtual destructor. SubProcess manages its child pointers via RAII and deletes all owned children upon destruction. In addition, WorkItemDecorator takes ownership of its wrapped component and deletes it in its destructor. When WorkflowInstance is deleted, its root SubProcess recursively frees the entire composite tree."

Q10: Why are WorkItemAction objects commands rather than simple methods on WorkflowEngine?

"Encapsulating user operations into Command objects (ClaimAction, StartAction, CompleteAction, RejectAction, DelegateAction, CancelAction) decouples the invoker from the execution logic. It allows commands to be validated before execution, logged into an execution history log, decorated with snapshots for transactional Memento rollback, and executed across different client interfaces (TUI, REST API, or automated test runners)."

Q11: How does TIVIDY support SLA deadlines and time-based escalations?

"Tasks can be assigned an SLA deadline in hours via the blueprint (deadline | id | hours). TividyWorkflowFacade exposes advanceClock(hours), which triggers the engine to scan all running instances. If a task in Available or InProgress has exceeded its deadline, it is automatically escalated, incrementing its escalation level and notifying the monitoring observers."

Q12: How do you prove that your engine handles multiple industries generically?

"Our repository contains 5 completely distinct industries: University Admissions (Education), Shipment Exceptions (Logistics), Hospital Admissions (Healthcare), Insurance Claims (Insurance), and Production Orders (Manufacturing). All 5 load, validate, route, execute, escalate, and terminate on the exact same compiled C++ engine binary without a single hardcoded `if-industry` branch."

Q13: Why did you keep disallowed actions selectable in the TUI?

"Because hiding disallowed buttons masks whether business logic is enforced by the UI or the engine. By keeping disallowed actions selectable, users and markers can actively attempt illegal operations (such as completing an unstarted task or delegating to an unqualified role) to witness the engine's polymorphic WorkItemState and RoutingStrategy explicitly refuse the action and explain why."

Q14: How does DepthFirstWorkItemIterator protect against null pointers or circular references?

"DepthFirstWorkItemIterator traverses the tree pre-order using an explicit std::stack rather than recursion. In our latest patch, it explicitly guards child pointers before pushing them onto the pending stack. WorkItem trees are acyclic directed trees enforced at build-time by FileWorkflowDefinitionBuilder, guaranteeing deterministic, termination-safe iteration."

Q15: Why are participant rosters isolated per context?

"In enterprise architectures, different departments or companies have independent directories. By isolating rosters per context in ParticipantDirectory, participant IDs (like 'clerk1') and role names can exist across different scenarios without collisions, while preventing unauthorized cross-department task assignments."
